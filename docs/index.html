What happens when you press send?

Between your click and the first word of the reply, your message crosses the internet, passes three checkpoints, waits in line and is read by a chip in a datacenter. It usually all takes well under a second. This chapter lets you run that machine and find out what makes it slow.

What's going on

When you press send, your app packs your message into a request: the conversation so far, plus any hidden instructions the app adds. The request crosses the internet to a datacenter, a building full of computers. A gateway checks who you are, a quick safety check screens the message, and then it waits in line until a copy of the model has room for it.

The model then works in two very different ways. First it reads. Your text is cut into tokens, small pieces of words (the next chapter shows how), and every token goes through the model at the same time, in one pass. Your last message was – tokens, read in –. Then it writes, one token at a time: each new token is fed back in to make the next, about one every –. Every token is sent to you the moment it exists, which is why replies appear word by word.

So the wait for the first word is the trip, the line and the reading, plus any thinking. Yours was – with the service – busy. A long prompt makes the reading longer. A busy service makes the line longer, and much longer near full. A thinking model writes hundreds of hidden tokens before the first one you see. After the first word, the writing pace barely changes.

How it works requests, queues, caching, two phases

The request. Apps send an HTTPS request to the provider's API (the address programs use to talk to the service). Its body is a list of messages (hidden "system" instructions, your turns, the model's turns), the model's name, a length limit and a flag asking for the reply to be streamed. The model keeps nothing between requests, so the whole conversation is sent again every turn70. With streaming on, the reply comes back as server-sent events: one long-lived response that delivers small chunks as they are made55.

Hidden instructions. A chat app adds its own instructions, and a coding agent adds even more: rules, tool descriptions and project files. The simulation uses 2,000 and 15,000 tokens; these are illustrative, and real apps vary. Your own code sends only what you write.

The line. Each copy of the model works on a limited number of conversations at once. The simulation's line is a classic single-queue model, M/M/1: requests arrive at random, and places free up at random. Its average wait is the time to free one place (60 ms here) times ρ/(1 − ρ), where ρ is how busy the service is. At 50% busy that is 60 ms; at 95% it is over a second. Providers keep spare capacity because waits explode near full.

Caching the start. If a request begins with exactly the same tokens as a recent one, the server can reuse the notes it made while reading them instead of reading again. Routers try to send you to a copy that has your conversation's start stored. Providers bill cached text at a discount7172. Chapter 7 shows where those notes live.

Two phases. Engineers call reading prefill and writing decode, and measure them as time to first token (TTFT) and time per output token. Prefill is limited by how fast the chips calculate, since every token can be processed in parallel. Decode is limited by how fast the chips can read the model's weights from memory, once per token. The two are so different that some systems run them on separate groups of GPUs3637.

What's going on

A model can only do arithmetic, so text has to become numbers first. A tokenizer cuts text into tokens, pieces taken from a fixed list called the vocabulary, and swaps each piece for its ID number. It starts from bytes: computers store every character as one to four small numbers between 0 and 255, so 256 starting tokens can spell any text in any language, emoji included.

The rest of the vocabulary is learned by byte-pair encoding: count every pair of neighbouring tokens in a large training text, glue the most common pair into a new token, and repeat. Your tokenizer has learned 0 merges from everyday English; the latest glued – into –. It cuts your 0 characters into 0 tokens, – per word. Real tokenizers learn from billions of words and keep tens of thousands of merges, so most common English words become a single token. On average an English token is about three-quarters of a word202.

Then each ID picks one row of the embedding table: a list of numbers the model learned for that token during training. From here on the model works only with those numbers. That's the catch with “strawberry”: the model receives one or a few IDs, not ten letters, so it can only count the r's if it has learned how each piece is spelled.

How it works bytes, merges, vocabulary size, embeddings

Bytes first. Text is stored as UTF-8: English letters take one byte each, accented letters two, Hindi letters three, most emoji four. GPT-2, OpenAI's 2019 model, ran byte-pair encoding on bytes instead of characters, so its tokenizer could encode any input without an “unknown” token. Its vocabulary stopped at 50,257 tokens63. The dashed boxes in the simulation are bytes that are only part of a character.

Words first, then merges. Before merging, text is split into rough words with a fixed pattern, so a merge never glues the end of one word to the start of the next. The space goes with the word after it, which is why you see “·the”. The simulation uses GPT-2's pattern63. Byte-pair encoding itself began as a 1994 file-compression trick, and was adapted for language in 2015 to split rare words into common pieces4.

How big a vocabulary? More merges make text shorter, so more fits in the model's working memory and each reply needs fewer steps. But every token adds a row to the embedding table and a choice to every prediction, and late merges glue rare pairs that save little, as you can see in the simulation. Meta's Llama 3 models use about 128,000 tokens9.

Languages cost differently. A tokenizer learns most merges for the languages that fill its training text. Text in rarer languages is split into more, smaller tokens, and how many tokens a word needs on average varies widely between languages64. Prices, speed limits and the model's maximum input are all counted in tokens, so the same message can cost more in one language than another.

Spelling is hidden. Because the model sees token IDs, anything about letters (spelling, rhymes, counting characters) has to be learned indirectly. A 2024 study found models can usually tell which letters a word contains but often miscount them, especially letters that appear more than twice201.

Embeddings. Looking a token up is just reading one row of the table. The rows start random and are adjusted during training (chapter 13) until tokens used in similar ways end up with similar rows. With older word-level models, researchers found that even directions in this space carried meaning, like a consistent step from “man” to “woman”56.

What's going on

At every step the model looks at the text so far and gives every word it knows a probability, a chance between 0 and 100%. Those are the bars. Then a random number picks one word, with each word's chance equal to its slice of the strip. The chosen word is added to the text and the whole thing repeats. That's all "writing" is: predict, pick, append, again. Words still in the running right now: 0.

The dice matter. With temperature 0 the top word always wins, and the model loops. Raising the temperature flattens the odds so less likely words get a turn; too high and it writes word pairs it never saw (0 in its last 40 words). Top-k and top-p fix that from the other side: they throw away the long tail of unlikely words before the roll. Chatbots use these same knobs, usually set by the company running them.

When the model reads a sentence instead of writing, we can measure how surprised it is by each true word: a word it gave 90% costs about 0.1, a word it gave 1% costs about 4.6. The average surprise is called the loss. On sentences it studied, your model's loss is –; on new sentences it is –. Training a model means nudging it, again and again, so that this number goes down.

How it works logits, samplers and loss

Your tiny model. It is a genuine language model, just a very small one. It learned from 49 short sentences written for this course, 155 different words in all, by counting which word follows each pair of words. When it has never seen a pair, it falls back to what follows the last word alone, and then to how common each word is. That fallback is where the "word pairs it never saw" come from. A large model replaces counting with a neural network that can generalise, and its vocabulary is far larger: Meta's open Llama 3 models choose among about 128,000 tokens at every step9. The sampling step works the same way.

Logits and softmax. A real model's last layer outputs one score, called a logit, for every token in its vocabulary. A function called softmax turns those scores into probabilities that add up to 100%. Temperature divides every score before the softmax. A component called the sampler then applies top-k (keep the k best), top-p, also called nucleus sampling (keep the smallest set of top tokens whose chances reach p), and draws one39. Sampling is the only random step: at temperature 0 the same prompt gives the same reply, apart from tiny differences in how a server adds up numbers.

Loss. The surprise −ln p of the true next token, averaged over all the text, is the cross-entropy loss. It is the one number every training run watches go down, and lower loss on held-out text (text the model never trained on) generally tracks a more capable model1. Your model's loss on its own sentences is low because it has nearly memorised them. That's why researchers always measure on text the model has not seen.

Why models make things up. Next-word prediction rewards text that sounds right. Usually that is also true. When the model hasn't learned a fact, a fluent guess can still look likely, and the model doesn't notice. Your tiny model shows the root cause: at temperature 1 it happily writes grammatical sentences that were never in its training text.

What's going on

Inside a model, every word is a list of numbers, a vector. On its own, the vector for "it" knows only that it is a pronoun. Attention is how a word gathers what it needs from the words before it. Each word makes a query (what am I looking for?) and every word offers a key (what do I contain?). The better a key matches the query, the more of that word's information, its value, flows in.

Attention only looks back. A model writes left to right, so when it is at "it" the last word doesn't exist yet. That's why "it" splits its attention, ? to the animal and ? to the street. The question is settled at the deciding word: "?" sends ? to the animal and ? to the street. When you change that word, nothing before it moves.

A model runs many of these attention heads side by side, each looking for something different: one follows meaning, one just looks one word back, one parks on the first word when there's nothing to fetch. They sit inside a stack of layers. In each layer, attention adds what it gathered to the word's vector, then a small network called the MLP works on the result. How it works queries, keys, values and the stack

Your toy model. Every number in the simulation is computed, not drawn by hand, but the model is tiny and its weights are set by hand. Each word has a few labelled numbers (is it a living thing, a place, a pronoun, a word that describes a living thing or a place). Real models learn thousands of numbers per word from data, and most of them have no simple label. Researchers have still found heads in trained models that track the previous word, heads that link a word to what it refers to, and heads that dump spare attention on the first token, an "attention sink"61. The tired/wide sentence pair is the example Google used to introduce the Transformer, the design these models use57. That first Transformer read in both directions; a model that writes left to right can only make the link at the deciding word.

Queries, keys and values. Each head multiplies a word's vector by three learned grids of numbers (weight matrices) to get its query, key and value. It scores the word's query against the key of every word up to and including itself, scales the scores, turns them into weights that add to 100% with softmax, and adds up the values with those weights5. Blocking every later word is called the causal mask. The previous-word head in the simulation finds its target the way real models usually encode position: queries and keys are rotated by an angle that grows with position (a method called RoPE), so the score depends on how far apart two words are.

The stack. A model like Meta's open Llama 3 8B, an 8-billion-parameter model, has 32 layers, each with 32 attention heads, and every word carries 4,096 numbers9. Each layer adds its results onto the word's vector rather than replacing it, so information builds up as it flows upward; this running vector is often called the residual stream. After the last layer, the final word's vector is turned into the next-token probabilities you met in chapter 3.

The cost. Every word scores every earlier word, so the work grows with the square of the length: double the text, four times the scores. The keys and values of earlier words are exactly the notes a server keeps in memory while it writes (chapter 7), and tricks like FlashAttention compute attention in small tiles to avoid slow memory traffic44. For a picture-by-picture walkthrough, Jay Alammar's illustrated guide is a good next read47.

What's going on

A model writes one token at a time, and each token gets the same fixed amount of computation. A hard problem can need more work than one token's worth. A thinking model (also called a reasoning model) gets around this by writing its working-out first: trying cases, checking, backing up. These thinking tokens are ordinary tokens, but the app hides them or shows a summary. Every one of them is something the model can look back at when it writes the final answer.

Spending more effort while answering is called test-time compute. On hard problems it helps a lot, then levels off: once the model has worked a problem through, it stops, and the unused budget buys nothing. Another way to spend compute is to run several attempts and take a majority vote. Right answers tend to agree while wrong ones scatter, so the vote beats a single attempt.

None of it is free. Thinking tokens are written one at a time, so they add waiting before the first visible word, and providers bill them like any other output. How it works training, scaling and budgets

Writing the steps out. Researchers found early on that asking large models to show their working, by giving examples with the steps written out ("chain of thought"), made them much better at maths word problems505. Reasoning models are trained to do this by themselves, at length.

Trained by checking answers. The training method is reinforcement learning: the model tries a problem many times, and attempts that end in the right answer are rewarded. This works best on problems whose answers can be checked automatically. DeepSeek, a Chinese AI lab, rewarded its R1-Zero model only for a correct final answer (maths answers compared with the known result, code run against tests) and for putting its reasoning between <think> tags. Nobody wrote reasoning for it to copy. Over training its answers grew longer by themselves, and it began to re-check and correct its own steps19. OpenAI, the company behind ChatGPT, describes training its o1 model the same broad way and reports that accuracy keeps rising with both more training and more thinking time501.

Where extra thinking pays. A study from Google DeepMind and UC Berkeley found that the best way to spend test-time compute depends on how hard the question is. Giving easy questions little and hard ones more was about four times as efficient as a fixed strategy. On easy and medium questions, a small model given extra thinking could beat a model 14 times larger, but on the hardest ones, a bigger model still won502.

Voting. "Self-consistency" samples several independent chains of reasoning and keeps the most common final answer. It lifted accuracy on a set of school maths word problems by about 18 percentage points over a single chain503. It multiplies the cost by the number of attempts. They can run side by side, so the wait grows much less.

Budgets in practice. With Anthropic's extended thinking, the developer sets budget_tokens, the most the model may spend on thinking. The minimum is 1,024 tokens, the model may use less, and thinking tokens are billed as output tokens504506. Serving them is like serving any other output: each one is a full pass through the model, and each one adds notes to GPU memory, which Chapter 7 shows is the scarce resource.

Patches. The idea comes from the Vision Transformer, a 2020 model from Google whose paper was titled “An Image is Worth 16x16 Words”. Resolution and cost. Apps shrink large photos before sending them, and providers count picture tokens much like the simulation. How it works booking, paging and sharing

Booking the maximum. Early servers didn't know how long a reply would be, so they reserved one unbroken stretch of memory for the longest allowed conversation. Most chats are far shorter, so most of each booking sat empty: the striped squares in the simulation. When the vLLM team measured real servers, 60–80% of the memory set aside for notes was wasted this way34.

Paging. vLLM borrowed an idea from operating systems: split memory into small fixed-size blocks (typically 16 tokens) and give each conversation a block only when it needs one. In the simulation one square stands for 1,024 tokens so you can see it; real blocks are much smaller.

When paging runs out. With paging, a conversation can grow until memory is full. The server then pauses the newest conversation, frees its blocks and puts it back in line, as you may have seen.

Sharing a beginning. Apps add the same hidden instructions to the start of every chat. If several conversations start with exactly the same tokens, their notes are identical, so the server can store them once and point every conversation's table at the same blocks. This is prefix caching, and it's why providers bill repeated prompt text at a discount71.

How it works rooflines, scheduling and quantisation

Memory-bound. Engineers compare a job's sums to the bytes it moves. Writing one token does about one sum per byte of weights for each person in the batch. An H100 can do about 295 sums in the time it reads one byte (989 trillion 16-bit sums a second against 3.35 TB a second of memory reads)23. So decoding, the token-by-token writing phase, is limited by memory until batches reach a few hundred people. Reading a prompt is different: it handles thousands of tokens in one pass, so it keeps the maths busy. This picture, a "roofline" with memory speed on one side and maths speed on the other, is the standard way to reason about it.

Continuous batching. Replies have very different lengths. A server that waits for a whole batch to finish before letting anyone new in leaves seats empty while one long reply finishes. Modern servers schedule one step at a time instead, so a finished seat is refilled straight away. The idea came from a system called Orca35 and is now standard, combined with the paged memory from the last chapter34.

Smaller numbers. Weights are usually trained and stored as 16-bit numbers (a format called BF16). Rounding them to fewer bits is called quantisation. At 8 bits the model takes half the memory; one early method did this for a 175-billion-weight model "without performance degradation"802, and a large 2024 study found 8-bit floating-point weights (FP8) effectively lossless at every size it tested, with well-tuned 4-bit weights close behind801. The loss depends on the model: a study of this exact Llama 3 model found noticeable losses at low bit widths, growing as the bits shrink803. In the simulation, 4-bit weights are unpacked to 16-bit for the sums, as common "weight-only" methods do, so they save reading but not maths. Real 4-bit files keep a few parts at higher precision, so they're a little bigger than a quarter. The notes stay 16-bit here, though servers can shrink those too.

What's going on

A model is a big calculation with adjustable numbers in it, the weights (also called parameters). Training means finding weights that make good predictions. For a language model the prediction is the next token (chapter 3). Here it's the height of a curve. The procedure is the same.

First, the model needs a score for how wrong it is. That score is the loss. Here it's the average of every miss, squared, so big misses count extra. Right now your network has taken 0 steps and its loss is 0. A language model's loss measures how surprised it was by the real next token.

Then it needs to know which way to move each weight. Picture the loss as a landscape, with one direction for every weight. The model can't see the landscape, but it can feel the slope under its feet. That slope, worked out for every weight at once, is the gradient. Each step moves every weight a little way downhill: gradient descent. The learning rate sets the step size. Too small and progress crawls. Too big and every step jumps over the valley floor.

Finding the slope for every weight is the clever part. Starting from the error, the calculation runs backwards through the network, and each layer works out how much it contributed and passes the blame to the layer before. This is backpropagation, the amber pulses. Your network has 97 weights; a large language model has hundreds of billions. The loop is the same.

How it works the network, optimisers, and training a real model

The network in the simulation. One input (the dot's position), two layers of "neurons", one output (the guess). Each neuron adds up its inputs, each multiplied by a weight, adds one more number of its own (a "bias", counted among the weights here), and squashes the result into a smooth S-shape. Squashed pieces added together can bend into almost any curve; more neurons, more bends. With one neuron per layer the curve can only go one way, always up or always down. The loss is the mean squared error, and backpropagation is written out by hand.

The landscape. The real landscape has one direction per weight, 97 here, so it can't be drawn. The picture is a flat slice through it, chosen to pass through three points of your run: the start, the halfway point and now. Every pixel's colour is the true loss at that point of the slice, so the path is real, but the slice hides the other directions.

Smarter steps. Plain gradient descent moves each weight by the learning rate times its slope. The simulation uses Adam, which keeps a running average of each weight's slope (a kind of momentum) and of its typical size, and divides one by the other. Every weight then moves about the same distance per step, whether its slope is steep or shallow58. The most widely used optimiser for language models is AdamW, a variant that also shrinks the weights slightly on every step68.

From this toy to a language model. Here every step looks at all 40 dots. A language model can't look at all its training text each step, so each step uses a batch of a few million tokens (a few dozen books' worth), which gives a noisy but useful estimate of the slope. The learning rate follows a schedule: a short warm-up, then a slow decay. Typical peak learning rates are 0.0001 to 0.001, far smaller than what works in this toy, and large slopes are clipped so one bad batch can't throw the weights far1.

What it costs. The backward pass costs about twice the forward pass. That's why training costs about 6 calculations per weight for every token read, against 2 to use the model7. It also has to keep every layer's results from the forward pass in memory until the backward pass needs them, one reason training needs far more memory than serving.

Some recover; others force the team to go back to an earlier saved copy and change something. DeepSeek, a Chinese AI lab, reported that its V3 model's run had no spikes it couldn't recover from and no rollbacks, notable enough to put in the report10. With 1,000 examples the model has picked up the format, and only 0% of its replies still just continue the text. It also copies the examples' habits, good and bad.

Judged. Writing perfect answers is hard; saying which of two is better is easy. So people compare pairs of replies, and a second model, the reward model, learns to predict their choices. The assistant then practises: it gives replies, gets scored, and shifts toward higher scores. Right now helpful replies have gone from 0% to 0%.

The leash. The reward model is an imitation of people, with flaws. People sometimes prefer an answer that agrees with them, and the reward model learns that too. Chase its score with nothing holding you back and the model finds those flaws: flattery wins. This is reward hacking. So training adds a penalty for drifting from the starting model, set by β. The drift now is 0.

Proven. Test scores are noisy: which questions get drawn is luck. With 100 questions, a score is only known to within about ±10 points. A gain counts only when the test is big enough that the two ranges stop overlapping.

How it works fine-tuning, feedback and evaluation

Supervised fine-tuning. The training is the same guess-and-nudge loop as before, on conversations instead of web text. Special tokens mark who is speaking (system, user, assistant), and usually only the assistant's tokens count toward the error. Datasets range from thousands to millions of conversations, written by people or generated by stronger models1. Generating training data with a stronger model is a form of distillation: a small "student" learns from a big "teacher's" outputs, an idea Hinton and colleagues set out for neural networks in 20151502. DeepSeek, for example, distilled reasoning from its R1 model into V310.

Fine-tuning cheaply. Updating every weight needs the full training setup from the last chapter. LoRA freezes the model and trains two thin extra matrices beside each layer; for GPT-3 it cut the trainable numbers about 10,000-fold and memory about threefold, with similar quality1501. That's how most companies customise open models.

Learning from feedback. OpenAI's InstructGPT set the recipe: fine-tune, collect rankings, fit a reward model, then optimise against it with reinforcement learning and a KL penalty (a measure of drift) to the starting model16. Push harder against a learned reward and the true quality rises, then falls, a pattern measured by Gao and colleagues1504; agreeable answers are one known flaw of human and model preferences1503. Variants: Constitutional AI has the model critique its own answers against written principles17; DPO skips the separate reward model and trains on the preference pairs directly18; for maths and code, rewards can come from checking the answer or running tests, which DeepSeek-R1 showed can teach long reasoning19. The simulation's numbers are illustrative; its formula for the trained model is exact.

Evaluation. Benchmarks are sets of questions with known answers, such as HumanEval's 164 coding problems1. Pitfalls: noise from small tests, contamination (test questions leaking into training data, which inflates scores), and sensitivity to how questions are worded. Hugging Face's advice is to reproduce published scores first and read the answers by hand20. Safety testing adds red-teaming: people and automated tools try hard to make the model misbehave. Anthropic ties required safeguards to the capabilities such tests find21, and checking continues after launch: its September 2025 postmortem describes production bugs that offline tests missed30.

What's going on

An agent is a model inside a loop run by ordinary software, the harness. The harness tells the model which tools exist, such as "run the tests" or "edit a file". When the model wants one, it writes a short structured request instead of a reply. The harness runs the tool, adds the result to the conversation and calls the model again. The loop ends when the model answers instead of asking40.

The model remembers nothing between calls. Everything it knows about the task must be in its context window, and that window has a hard limit. So the harness's main job is choosing what goes in. Too little and the model guesses. Too much and it overflows, or the one important line gets lost among unrelated text41.

That's why harnesses search instead of pasting everything. Ahead of time the code is cut into chunks, and each chunk becomes a list of numbers called an embedding, so chunks with similar meaning get similar numbers (the dots on the right). The model's query becomes numbers the same way, and the nearest chunks are pasted in. This is retrieval-augmented generation, or RAG1601.

Re-reading is also what makes agents expensive. Your last task made 0 calls that read 0 tokens in total, though the context never held more than 0. How it works tool calls, MCP, retrieval, compaction, caching

Tool calls. Each tool is described to the model by a name, a sentence about what it does and a schema for its inputs. The model replies with a structured request such as edit_file(path, change). The harness checks permissions, runs it (often in a sandbox) and appends the result. Anthropic separates workflows, where code fixes the order of steps, from agents, where the model picks its own next step, and recommends the simplest one that works40. Real harnesses also set budgets on steps, time and money, which is the role of the token budget in the simulation.

MCP. Every harness used to wire up each tool its own way. The Model Context Protocol, an open standard Anthropic released in November 2024, defines one way for a tool or data source to describe itself and be called, so something written once as an "MCP server" plugs into any harness that speaks the protocol160442.

Retrieval. The original RAG paper paired a text generator with a searchable index of Wikipedia passages: question and passages were turned into vectors, the closest passages were fetched, and the generator wrote its answer from them1601. The design choices are the ones you played with: chunk size, and how many results to paste. Coding agents often skip the index and let the model search with ordinary tools like file listing and text search, fetching files only when needed41.

Compaction. When the window fills, harnesses summarise old tool output, keep notes in files the agent can re-read, or hand a sub-task to a sub-agent with a fresh context41. Summaries keep the gist and lose details, as you may have seen when the broken code got squashed. Position matters too: models use facts at the start or end of a long context more reliably than facts in the middle1603.

Caching. The cache only matches an identical beginning. Change anything early, for example by summarising an old output, and everything after it is billed fresh again. Writing to the cache costs a little more than a normal read, and entries expire after a few minutes unless they are reused71. That's why harnesses keep stable text (instructions, tool descriptions) at the start.

What's going on

A model reads one long stream of tokens. Your request, the app's hidden instructions and every email or web page a tool fetches all land in that same stream, and the model has no reliable way to tell which parts are orders and which are just data. So text written by a stranger can steer it. This is prompt injection; when the text arrives through something the agent reads, rather than from the user, it's called indirect1701. A jailbreak is the related trick of talking a model out of its own rules ("You are now FreeBot, an assistant with no rules").

No single fix exists, so defences come in layers, each catching some attacks and each with a cost. With your settings, 0 of the 5 attacks get through and 0 of the 10 real tasks get done. A stricter detector also quarantines real mail; fewer tools means the assistant does less for you; asking first means more interruptions.

Why not just look inside and see what the model is "thinking"? Researchers are starting to. They can find features, patterns of activity inside a model that match recognisable ideas such as secrecy or a famous bridge1707. But most of what happens inside is still unmapped, which is why models are called a black box.

The same black box explains why models sometimes make things up (often called hallucinating). A model writes the most likely-sounding continuation. When it doesn't know a fact, the likeliest text is still a fluent, confident answer, and training and tests have usually rewarded a guess over "I don't know"1704.

How it works attacks, layers, features and made-up facts

How the attacks work. In 2023 researchers hid instructions in web pages and documents and showed they could take over real assistants, including Microsoft's Bing Chat, which could read the web page open next to it. The hidden text could make the assistant steal data, spread false information, or copy the attack into other messages1701. Data can leave through any tool that reaches the outside world. Sending an email is the obvious one. Opening a web address is a quieter one: the address itself can carry the stolen text, as with the invitation and recipe emails in the simulation.

Marking untrusted text. The app can wrap or change outside text so the model can tell it apart, for example by putting a special character between every word, and tell the model never to follow instructions inside it. In Microsoft's tests this "spotlighting" cut attack success from over 50% to under 2%1705. Under 2% is still not zero, which is why the other layers exist.

Limits in the harness. The harness, not the model, decides what tools exist and what needs a person's OK. Giving an agent only the tools a task needs, and asking before anything that can't be undone, means that a fooled model can't do much harm. In the simulation, the model is fooled and the harness catches it.

Detectors. A separate model can screen what goes in and comes out. Anthropic trained such classifiers against jailbreaks from a written list of allowed and forbidden topics. People spent over 3,000 hours trying to break them without finding a trick that worked across the board. The cost: slightly more refusals of harmless requests (0.38 percentage points) and about 24% more computing1702. Other detectors watch the model's own internal activity, and spot when outside text pulls it away from the user's task1703. The bottom panel in the simulation shows that idea, with made-up lamps.

Looking inside. Inside a model, an idea is spread across many numbers at once. A technique called dictionary learning untangles them: in Claude 3 Sonnet, Anthropic found about 34 million features, including ones for secrecy, for deception and for security holes in code. Turning a feature up changes behaviour: with the Golden Gate Bridge feature at ten times its usual strength, the model began to describe itself as the bridge1707. Researchers can also trace how features feed each other into "circuits", step by step through a single answer1706.

Why it makes things up. OpenAI researchers point to two causes. First, from training: some facts, like a little-known person's birthday, appear only once in all the training text, so there is no pattern to learn them from. They showed that the share of such once-seen facts sets a floor on how often a freshly trained model gets that kind of fact wrong. Second, most tests mark an answer right or wrong and give nothing for "I don't know", so a model that always guesses scores higher, like a student guessing on a multiple-choice exam1704. Inside the model, Anthropic found a circuit that says "I can't answer" by default, switched off when the model recognises a name. If a name feels familiar but the facts aren't there, that switch can misfire, and a confident made-up answer comes out1706.

Rent two GPUs for an hour. Run the same training job twice: once with a full copy of the model on each GPU, once with the model's state split between them (FSDP).
