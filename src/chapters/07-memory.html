Chapter 7 · Serving millions

Why do long chats get slower and pricier?

While a model writes, it keeps notes on every word so far. Those notes live in the GPU's memory, and they fill it up long before the GPU runs out of maths. This chapter puts you in charge of that memory.

What's going on

To write each new word, the model looks back at every word before it. For each earlier word it needs two small lists of numbers, a "key" (what this word is about) and a "value" (what it contributes). Working these out again for every new word would mean re-reading the whole conversation over and over, so the server keeps them. That store of notes is the KV cache.

The notes are small per word but add up fast. For the model in the simulation, every token needs 128 KB of notes. A 30,000-token document needs almost 4 GB before the model writes a single word, about a quarter of the model's own size. Right now your GPU holds 0 tokens of notes (0 GB) for 0 conversations.

So the number of people a GPU can serve is set by memory, not by how fast it calculates. That makes memory management the main job of a serving system, and it explains two common facts. Long chats cost more per message, and providers charge less for text they've seen before.

How it works booking, paging and sharing

Booking the maximum. Early servers didn't know how long a reply would be, so they reserved one unbroken stretch of memory for the longest allowed conversation. Most chats are far shorter, so most of each booking sat empty: the striped squares in the simulation. When the vLLM team measured real servers, 60–80% of the memory set aside for notes was wasted this way34.

Paging. vLLM borrowed an idea from operating systems: split memory into small fixed-size blocks (typically 16 tokens) and give each conversation a block only when it needs one. A small table records which blocks belong to whom, so they don't have to sit next to each other. Waste fell below 4%, and the same GPU served two to four times as many requests34. In the simulation one square stands for 1,024 tokens so you can see it; real blocks are much smaller.

When paging runs out. With paging, a conversation can grow until memory is full. The server then pauses the newest conversation, frees its blocks and puts it back in line, as you may have seen.

Sharing a beginning. Apps add the same hidden instructions to the start of every chat. If several conversations start with exactly the same tokens, their notes are identical, so the server can store them once and point every conversation's table at the same blocks. This is prefix caching, and it's why providers bill repeated prompt text at a discount71.

Making the notes smaller. Model designers shrink the notes too. This model lets 32 attention heads share 8 sets of keys and values ("grouped-query attention")9. DeepSeek compresses each token's notes into one small vector62.

The maths memory per token, step by step
In words

Every layer of the model keeps a key and a value for every token. Each is a list of numbers, one per attention "head", and each number takes 2 bytes.

With this model's numbers

2 (key and value) × 32 layers × 8 heads × 128 numbers × 2 bytes
= 131,072 bytes = 128 KB per token
Your GPU right now: 0 tokens × 128 KB = 0 GB

In symbols
M = 2 · L · h · d · b · n

M memory for the notes · L layers (32) · h key-value heads (8) · d numbers per head (128) · b bytes per number (2) · n tokens stored. Everything except n is fixed by the model, so memory grows in a straight line with the length of every conversation, and with how many there are.

128 KB Carry this forward

Every token a model is working on needs notes in GPU memory, 128 KB each for an 8-billion-parameter model. Memory, not maths, decides how many people one GPU can serve.
