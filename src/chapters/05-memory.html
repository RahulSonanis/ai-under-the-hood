Chapter 5KV cache

How does it remember the conversation?

Short answer

The model itself keeps nothing between messages. The conversation is stored outside it and fed back in with every request. While writing a reply, the model keeps notes on every earlier token (their attention keys and values) so it never recomputes them. Those notes, the KV cache, fill up GPU memory fast, and managing that memory decides how many people one GPU can serve.

Memory strategy

Llama 3 8B in BF16 takes about 16 GB; each token's keys and values take 2 × 32 layers × 8 KV heads × 128 dims × 2 bytes = 128 KiB9. At this picture's scale one square is about 167 MB, roughly 1,270 tokens of notes; real paged systems use much smaller blocks, typically 16 tokens. Older servers reserved space for the maximum length up front and wasted 60–80% of KV memory; vLLM's PagedAttention allocates small blocks on demand and cut waste to under 4%34. Request lengths are random.

Four different kinds of "memory"

The model forgets everything after each reply. The app (or the service behind it) keeps your chat and hands the whole thing back every time you send a message, like re-reading a letter thread before answering.

Conversation history: stored outside the model and fed back in each turn. KV cache: the model's scratch notes while writing one reply. Prefix caching: the server keeps notes for text many requests share, such as a system prompt, so it skips recomputing it. App memory: facts some apps save about you and paste into future prompts.

Conversation history is managed outside the model. With a stateless API the client resends the full message list70; some APIs instead store the conversation and restore it from a conversation or previous-response ID73. Either way, the model reads the whole history again as input. Providers reuse the KV cache for a repeated prompt prefix for a few minutes and bill those tokens at a discount7172. Persistent "memory" features are retrieval: saved text is inserted into the context window. None of the four changes the model's weights.

p(y_t | x, y_<t ; θ)

Each output depends only on the tokens in the window and the fixed weights θ. The KV cache memoises K = XW_K and V = XW_V for tokens already processed; a prefix cache shares those tensors across requests whose token prefix is identical (vLLM matches it by hashing fixed-size blocks34). Only training changes θ.

The KV cache

Imagine writing a story and, for each new word, re-reading the whole story from the start. Slow! Instead you keep sticky notes about each word you've already read. The model does the same.

Attention needs the "label" and "message" (key and value) of every earlier token. Those don't change once computed, so the server stores them. Each new token only has to compute its own and look at the stored ones. The store grows with every token and every conversation.

KV size per token = 2 × layers × KV heads × head dim × bytes. Llama 3 70B with grouped-query attention needs 320 KiB per token, so one 128k-token context needs about 43 GB, more than half an H100. Without GQA (64 KV heads instead of 8) it would be eight times larger. DeepSeek's multi-head latent attention instead caches a small compressed vector per token6210. Long context is mainly a memory problem.

s_KV = 2 · b · L · n_kv · d_head · n_tokens

(b bytes per element, L layers.) Without the cache, generating T tokens costs Θ(T²) recomputation of keys and values; with it, step t is Θ(t) attention work plus a constant amount of projection work, at the cost of Θ(t) memory. MLA stores ≈ 4.5·d_head values per layer per token instead of 2·n_kv·d_head621.

Paged memory and prefix caching

Instead of giving every guest a huge table "just in case", the restaurant hands out small tables as each group grows. Far more people fit.

The server doesn't know how long a reply will be. Reserving the maximum for everyone wastes most of the space. Handing out small blocks as needed packs memory tightly. And when many conversations start with the same instructions, those notes can be stored once and shared.

PagedAttention borrows virtual memory from operating systems: a per-sequence block table maps logical token positions to physical KV blocks, so memory needn't be contiguous. vLLM reported 2–4× higher throughput from this34. Blocks can be shared copy-on-write, which enables prefix caching: if a request starts with the same tokens as an earlier one (a long system prompt, a document, earlier turns of the chat), those blocks are reused and that part of prefill is skipped. API providers expose this as cheaper "cached" input tokens.

With block size B tokens, internal fragmentation is at most B−1 slots per sequence, so expected waste is about (B−1)/2 slots versus (max_len − len) under reservation. Prefix sharing turns KV memory into a trie keyed by token blocks; a router that sends requests to the replica holding the longest matching prefix ("KV-aware routing") raises the hit rate36.

Why does doubling the context length roughly halve how many conversations fit on a GPU?

Weights are fixed; each conversation's notes grow with its length, so twice the tokens means twice the memory per conversation.

Ten thousand users all send requests that start with the same 3,000-token instructions. What helps most?

Shared prefixes can reuse the same KV blocks and skip that part of prefill.
