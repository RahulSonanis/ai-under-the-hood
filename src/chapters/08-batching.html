Chapter 8 · Serving millions

How does one GPU serve many people at once?

To write a single token, a GPU reads every one of the model's billions of numbers from its memory. Reading them takes far longer than the sums it does with them. So servers make each read count: one pass over the model writes the next token for dozens of conversations at once.

About 15 minutes · one simulation · you'll learn why writing text is limited by memory reads, how batching shares them, when that stops working, and how smaller numbers make models cheaper to serve.

What's going on

A GPU has two parts that matter here: a large memory that holds the model, and maths units that do the sums. A pipe joins them, and the pipe is the slow part. To write one token, every weight has to travel through it. For the 8-billion-weight model in the simulation (Meta's open Llama 3 8B9) that's 16 GB per token. On an H100, a common data-centre GPU, reading it takes about 7 ms while the sums take a few hundredths of a millisecond. With one person, the maths units sit idle almost all the time.

Batching means serving many conversations in the same step. The weights are read once and used for everyone. Right now your GPU serves – at a time. Each step reads –, takes – and gives everyone one token, so each person gets – tokens a second. A million tokens cost –, against – if the GPU served one person at a time.

Two things end the free ride. Each person's notes are private, so they must be read too, and they grow with every token; long chats make the notes outweigh the model. And memory runs out: no room for notes means no seat. The other lever is the size of each number. Storing weights in 8 or 4 bits instead of 16 halves or quarters what has to be read, and frees memory for more people, at a small cost in accuracy.

How it works rooflines, scheduling and quantisation

Memory-bound. Engineers compare a job's sums to the bytes it moves. Writing one token does about one sum per byte of weights for each person in the batch. An H100 can do about 295 sums in the time it reads one byte (989 trillion 16-bit sums a second against 3.35 TB a second of memory reads)23. So decoding, the token-by-token writing phase, is limited by memory until batches reach a few hundred people. Reading a prompt is different: it handles thousands of tokens in one pass, so it keeps the maths busy. This picture, a "roofline" with memory speed on one side and maths speed on the other, is the standard way to reason about it.

Continuous batching. Replies have very different lengths. A server that waits for a whole batch to finish before letting anyone new in leaves seats empty while one long reply finishes. Modern servers schedule one step at a time instead, so a finished seat is refilled straight away. The idea came from a system called Orca35 and is now standard, combined with the paged memory from the last chapter34.

Smaller numbers. Weights are usually trained and stored as 16-bit numbers (a format called BF16). Rounding them to fewer bits is called quantisation. At 8 bits the model takes half the memory; one early method did this for a 175-billion-weight model "without performance degradation"802, and a large 2024 study found 8-bit floating-point weights (FP8) effectively lossless at every size it tested, with well-tuned 4-bit weights close behind801. The loss depends on the model: a study of this exact Llama 3 model found noticeable losses at low bit widths, growing as the bits shrink803. In the simulation, 4-bit weights are unpacked to 16-bit for the sums, as common "weight-only" methods do, so they save reading but not maths. Real 4-bit files keep a few parts at higher precision, so they're a little bigger than a quarter. The notes stay 16-bit here, though servers can shrink those too.

The maths how long one step takes
In words

A step takes as long as the slower of two jobs: reading everything (the weights once, plus every person's notes) through the pipe, or doing the sums (two per weight, for each person). Each person gets one token per step.

In symbols
tread = (W + B·c·k) ÷ BW
tsums = 2·N·B ÷ F
t = max(tread, tsums)

t time for one step, the larger of the reading time tread and the sums time tsums · W bytes of weights (16 GB at 16-bit) · B people in the batch · c tokens in each conversation · k bytes of notes per token (128 KB) · BW memory speed in bytes per second (70% of 3.35 TB/s) · N number of weights (8 billion) · F sums per second (50% of peak). Speed per person = 1 ÷ t; total = B ÷ t; cost per token = (price per second × t) ÷ B. While W dominates, t barely grows with B, so cost falls almost as 1 ÷ B.

One read, many people Carry this forward

Each step reads all the weights once; batching shares that read across many conversations, until their notes or the memory run out.

Check yourself

Why do long conversations make each token more expensive to serve, even with plenty of people in the batch?

Notes aren't shared, so they add to every step's reading, and they take memory that could seat more people.

A server stores the model's weights in 8 bits instead of 16. What is the main gain for a busy chat service?

Reading the weights is the slow part, so halving their size speeds every step and frees memory for more people. Tests find 8-bit models almost as accurate as 16-bit ones.
