How does one GPU serve many people?

Short answer

To write one token, a GPU must read all the model weights it uses from its memory. Reading is the slow part, so it writes the next token for many conversations in one go. When conversations are short and memory is free, each extra person barely slows the step, which is what makes AI affordable to serve. Long conversations and very large batches change that.

Why batching is nearly free

A chef has one giant recipe book in the pantry. To cook anything, they must carry the whole book to the kitchen. Carrying it is slow; cooking is fast. So if eight people want dinner, the chef carries the book once and cooks eight meals.

The "book" is the model's weights. For every new token, the GPU has to read all of them from memory. With one person, the GPU's maths units sit mostly idle while it waits for that read. Adding more people uses that idle maths, so total output rises almost in proportion while each person's speed barely changes, until the maths units are finally full.

This is the roofline model. A workload's arithmetic intensity is FLOPs per byte moved. Decoding a BF16 model does about 2 FLOPs per 2-byte weight per sequence, so intensity ≈ batch size. An H100's ridge point is 989 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOPs/byte, so decode stays memory-bound until batches of a few hundred, and in practice KV-cache reads and memory capacity cap the batch first. Prefill, which processes thousands of prompt tokens at once, is compute-bound.

t_step ≈ max( (W + B·c·s_kv) / BW , 2·N_act·B / F )

with W weight bytes, B batch, c context length, s_kv KV bytes per token, BW bandwidth, F peak FLOPs. Throughput = B / t_step; per-user speed = 1 / t_step. Cost per token = (GPU $/s) · t_step / B, which falls roughly as 1/B while weight reads dominate.

Continuous batching

A bus that only leaves when everyone from the last trip has got off wastes seats. A better bus lets someone new hop on at every stop.

Replies have very different lengths. If the server waits for the longest reply in a group before starting new ones, most seats sit empty. Scheduling one token-step at a time lets a finished seat be refilled immediately.

Iteration-level scheduling was introduced by Orca35 and is standard in vLLM, TensorRT-LLM and SGLang. Combined with paged KV memory it gives large throughput gains34. Production stacks add more: chunked prefill (splitting long prompts so they don't stall decoding), separate prefill and decode pools with the KV cache shipped between them3637, speculative decoding where a small model drafts tokens the big one verifies in parallel38, and quantisation to 8 or 4 bits so fewer bytes are read per step.

Under static batching a batch takes max(ℓ₁…ℓ_B) steps while doing Σℓᵢ useful work, so utilisation is E[ℓ] / E[max ℓ], which falls as length variance and batch size grow. Continuous batching keeps utilisation near min(1, λ·E[ℓ] / B) for arrival rate λ, until the queue saturates.

Check yourself

A dense model is decoding short conversations on a GPU with memory to spare. Going from 1 to 16 people in a batch, what happens to each person's speed?

At small batches the step time is set by reading the weights, which is shared across everyone in the batch. This holds while the step stays memory-bound: long contexts add KV reads, and very large batches become compute-bound.

Why do long conversations make serving more expensive per token?

KV reads add bytes per step, and KV memory limits batch size, so the weight read is shared by fewer people.
